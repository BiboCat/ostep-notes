#### 另一种优化目标

作者开篇就提出了"另一种类型的调度器"：

> In this chapter, we’ll examine a different type of scheduler known as a proportional-share scheduler, also sometimes referred to as a fair-share scheduler.

这个"另一种"，针对的是"调度器的优化方向/优化目标"而言的。

本章提出的调度器是`proportional-share scheduler`，CPU份额分配调度器。
前两章学习的调度器，它们的优化目标是"兼顾`response time`和`turnaround time`"，这种目标的核心是时间/时延。**而CPU份额分配的目标，关心的是某一个作业必须得到约定的CPU占用份额**，而什么时候跑完，则是次要的。

因此，本章讨论的问题就是：**如何设计一个按比例分享CPU的调度器**？

### Lottery

本章9.1-9.5小节都在讲其中一种实现方式`Lottery`。

**`Lottery`采取类似`RR`轮转的方式**，但是在每个时间片开始，需要选择下一个作业时的行为不同。

#### 一、核心机制：Ticket

- **`Lottery`选择作业、达到份额分配目标的方式，是依靠概率的。**
  假如想要作业A和B的CPU份额比是3:1，那么`lottery`在选择作业时，会让作业A被选择的概率是75%，作业B被选择的概率是25%。

- **而这种概率的形成，靠的是`Ticket`。**
  `Lottery`给每个作业发一定数额的`Ticket`：如作业A发150票，并记票号0-149；作业B发50票，并记票号150-199；总票数200。然后根据总票数200，在0-199区间随机取一个数字，落在哪个区间上就调度对应的作业。

#### 二、Ticket 的完整机制

9.2小节，作者完整说明了`Ticket`的分配、变动等机制。

**①不同用户下属作业的份额分配**：
`Lottery`可以首先站在用户视角，给不同的用户发"**全局`Ticket`**"，这确定不同用户分别占用的CPU总份额。
每个用户再可以给自己的作业分配份额。用户可以独立地通过分配`Ticket`控制自己的作业的CPU份额，这些独立发的用户票，只影响同属于该用户的作业的份额分配。

书上的例子是：用户A有100张全局票，用户B有100张全局票；A跑两个任务A1和A2，A给它们各发500张票；B只跑一个任务B1，B给它发了10张票。结果如下表：

| 用户     | 本地给票 | 本地货币总量 | 占比   | 折算成全局票  | 实际CPU份额 |
| ------ | ---- | ------ | ---- | ------- | ------- |
| A → A1 | 500  | 1000   | 50%  | **50**  | **25%** |
| A → A2 | 500  | 1000   | 50%  | **50**  | **25%** |
| B → B1 | 10   | 10     | 100% | **100** | **50%** |

**②作业间票的流动**：
`Lottery`规定，作业可以临时把自己的票交给另一个作业。
书上举例的场景是client和server：客户端发消息让服务器替它干活，为了让它干得快，客户端**把自己的票转给服务器**；服务器处理完，**再把票转回去**。——**这种流动是临时性的**。

**③作业临时改变自己票数：**
`Lottery`中，作业可以临时地调高或调低自己的票数。
这没什么好说的，只需要特别强调：**这只在不互相竞争的受信环境里合理**。

*——这些机制看看就好了，知道它们存在，并不难理解。*

#### 三、Lottery 的实现

它太好实现了，只需要三样：

- 一个好的随机数生成器

- 一个装作业的数据结构，比如链表

- 需要维护的总票数，一个变量`totalticket`

其他的逻辑实现，其实刚刚都有说了，但是书上还是讲解了，一次作业选取的过程，用代码表示：

```c
int counter = 0;
int winner = getrandom(0, totaltickets);   // 取 [0, totaltickets-1]
node_t *current = head;
while (current) {
    counter = counter + current->tickets;
    if (counter > winner) break;           // 落在这一段的票号里
    current = current->next;
}
// current 就是赢家
```

值得提起的是，如果将链表按票数从高到低排序，能减少平均遍历次数——因为`counter`涨得快！

最后需要注意的一点是，**每次决策的时间复杂度是O(n)**！

#### 四、其他分析

**①概率和期望的差别：**
以概率配置的份额分配，只有在样本足够大时（时间片轮数够多）才会完美分配。在短任务上，它相当不公平。

**②关于票如何分配的问题：**
一个新作业进入系统，需要给它分配票。但是**谁来分配？分配多少？**
由于份额占比有较强的主观性，且作业之间没办法互相商量，所以基本**靠人来分配**！并且"分配多少"这个问题，`lottery`直接推给了人！

总体来说，`lottery`就是一个特别简单的实现份额分配的算法。核心就两个字："随机"。不用过多地关注它了！

### Stride

`Stride`同样是采取`RR`轮转的方式的，与`RR`的区别也是在于选择方式。
`Lottery`是纯随机，而`Stride`则是靠记账。

#### 一、stride 和 pass

- **`stride`意为"步长"**，是`Stride`算法的一个重要量。`stride`的计算方式是：`stride = 大常数 / Ticket`，即它与`Ticket`成反比（大常数可以选择为票数们的公倍数）。——`Ticket`越多，`stride`越小。

- **`pass`是每一个作业的运行"账本"**。每个任务有一个`pass`，初始值为`0`，每次运行一轮，就把自己的`pass`加上自己的`stride`。——`Ticket`越多，`stride`越小，`pass`增长得越慢！

*然后是`Stride`算法的核心规则：*

- **每次选取作业时，选择`pass`最小的作业。**

从体感上看，这个算法能保持运行比例的平衡，但还是用**理论分析一下**更好：

首先明确一点的是，"作业的`Ticket`占比就是需要维持的份额占比"。

作业们有各自的`stride`，这些`stride`有一个最小公倍数`lcm`。这个最小公倍数就是：各个作业的`pass`除了初始的`0`之外，再次全部相等的值，并且以后再次出现全部相等时也将会是`lcm`的倍数。

在一个`pass`从相等到下一次相等的**调度周期**中，每个作业运行的次数是`lcm / stride`。同时，`stride`与`Ticket`成反比，各作业`lcm / stride`的比例就是`Ticket`的比例。至此推理完成，在一个**调度周期**内，作业`Ticket`的占比就是运行次数的占比。

具体例子是原文的`Figure 9.3`，按这个逻辑分析是对得上的。

**现在总结并评价一下`Stiide`**：

- 实现方面，它需要靠三个变量记录；遍历寻找最小`pass`时，采取最小堆可达   O(log n)的时间复杂度。

- `Stride`在一个调度周期内，份额比例是完全精确的，而非`Lottery`的长期概率收敛。

- **隐含一个关于收敛的问题，如果任务很多，`lcm`很大即调度周期很长，那么它的"周期内精确"会退化为"长期精确"。**

和`Lottery`一样，**`Stride`也没有规定`Ticket`的分配规则**，还得靠人来分配。并且，`Stride`比`Lottery`多出的一个问题是，新任务的`pass`设置问题——还是从0开始吗？

### CFS

`CFS`是升级版的`Stride`，原理类似，但解决了-许多问题-。

#### 一、动态计算时间片

`Stride`靠步长记账，而`CFS`使用时间记账——取消了`stride`和`pass`，改用`vruntime`记录运行时间。

先接触**无权重版**的`CFS`（也就是份额平均分配）。

- 每一轮选择`vruntime`最小的作业；

- **动态**计算该作业所获时间片`q`；

- 此轮结束后，按物理世界的时间给`vruntime`增加（跑了1ms就记录1ms）；

这里的关注点是有关`q`的，一个时间片应该为多少，这关乎一个调度周期——**一个调度周期内应该让每一个作业拥有一个时间片，并且一个周期后份额比例达到预期，`vruntime`增量全部相等。**

`sched_latency`意思是调度周期。在无权重的版本中，每个作业时间片的长度都相等：`q = sched_latency / n`（`n`是作业数）。

`min_granularity`意思是最小的时间片。它被用来防止时间片过小造成切换开销过大。

这两个参数先定好，然后时间片从中**动态**算出来：先算`q = sched_latency / n`，然后与`min_granularity`比较，如果计算的`q < min_granularity`，则采用`min_granularity`，否则采用计算的`q`。

#### 二、固定的权重份额

`CFS`取消了`Ticket`的概念，而是使用权重`weight`；同时，`CFS`不直接给作业发`weight`值，而是发`nice`等级，`nice`和`weight`有一张映射表！

```c
static const int prio_to_weight[40] = {
    /* -20 */ 88761, 71755, 56483, 46273, 36291,
    /* -15 */ 29154, 23254, 18705, 14949, 11916,
    /* -10 */  9548,  7620,  6100,  4904,  3906,
    /*  -5 */  3121,  2501,  1991,  1586,  1277,
    /*   0 */  1024,   820,   655,   526,   423,
    /*   5 */   335,   272,   215,   172,   137,
    /*  10 */   110,    87,    70,    56,    45,
    /*  15 */    36,    29,    23,    18,    15,
};
```

`nice`范围从`-20`到`+19`，共40个等级。正数优先级更低，负数优先级更高。
并且这个表其实是等比数列，公比约`1.25`。

咱们来看一下权重`weight`的作用：

**①计算时间片长度：**
`sched_latency`是一个调度周期，`CFS`不设定固定的时间片长度，每个作业的时间片动态计算，在一个调度周期内每个作业都有一个由自己`weight`决定的时间片。

```
                     weight_i
time_slice_i = ───────────────────── × sched_latency  ——公式①
               Σ weight_k (k=0..n-1)
```

如果计算出`time_slice_i`小于`min_granularity`，那么还是又`min_granularity`兜底，即选择`min_granularity`的值。

**②计算`verntime`的增长量：**
`CFS`规定，`weight`越大的，`vruntime`的增长速度应该越慢——从而高`weight`的能更常被选中。

```
                           weight_0
vruntime_i = vruntime_i + ────────── × runtime_i  ——公式②
                           weight_i
```

因此`CFS`的最终规则表述为：

- `nice`表示权重等级，等级映射的`weight`值固定；

- 每一轮选择`vruntime`最小的作业；

- **动态**计算该作业所获时间片`q`，使用公式①计算；

- 此轮结束后，按公式②给`vruntime`增加；

#### 三、分析和评价——五个话题

**①调度周期闭环：**

观察上面的两个公式，现假设`runtime_i = time_slice_i`，那么每一个作业每次运行后`vruntime`的增量都是相等的（`weight_i`被约分掉了）。

这意味着在一个`sched_latency`内，"调度周期"的含义被完美完成了：
**一个调度周期内应该让每一个作业拥有一个时间片（公式①），
并且一个周期后份额比例达到预期（公式①），
`vruntime`增量全部相等（刚才的结论）。**

**②`min_granularity`的影响：**

`min_granularity`的出现，打破了`sched_latency`的平衡。如果有`min_granularity`兜底的情况，那么在预设的`sched_latency`内就无法跑完所有的作业；并且采用`min_granularity`的作业，它的`vruntime`增量也会与其他作业不等。

但是这不会影响这个算法的正确性，**只是把"每一个调度周期比例平衡"变成了"部分极端任务在长期收敛平衡"，因为记账还在。**
一个直观的感受是：一个极低`weight`的作业，享受了`min_granularity`的保护，但是由公式②，它的`vruntime`比未受保护的情况增长更快，调用频率降低。

**③关于动态时间片：**

传统的`RR`时间片相等。在刚学它的时候，我们提到时间片应该是中断定时器的倍数，这样内核才能在需要切换的时候及时接管CPU。但在这里，时间片是动态的，中断计时器又不可能随时变化，怎么办？

实际上，不需要中断计时器进行匹配，这就是`runtime`和`time_slice`的区别（刚刚我们还假设它们相等）。

一个作业的`runtime`可以大于`time_slice`，直到内核接管CPU进行切换。但是作业多跑的部分，不是无代价的，同样会记录在`vruntime`账上，影响调用频率。这个问题同样是——**把"每一个调度周期比例平衡"变成了"任务在长期收敛平衡"**。

**④`nice`的设定：**

前面的`Lottery`和`Stride`的`Ticket`的分配完全都推给了人！但是在`CFS`中，每个进程有一个默认值`nice = 0`。

另外，新进程的`vruntime`初始值，一般会被设定成当前所有作业`vruntime`的最小值。

再说一个扩展的知识：进程`fork()`和`exec()`之后，`nice`继承或保留。

**⑤关于`nice`的观察：**

`nice`发挥作用的是差值。

两个场景，一个有两个作业（`nice_1 = 0`、`nice_2 = 5`），另一个也有两个作业（`nice_1 = 5`、`nice_2 = 10`），它们求出来的`time_slice`的情况是完全相同的，因为`nice`各级对应的`weight`是等比数列，公比1.25。

——可以在带入数据的时候，`weight_i`都写成`weight_0 * 1.25^(-i)`以验证......

#### 四、Using Red-Black Trees

书上9.7小节，简单提及了关于红黑树的使用。这是为了减少调度开销（查找方面）。现实中`CFS`确实也是这么干的。

其实作者自己也没说多少，我们也只做概念性的描述：

- 只有待运行的作业才放红黑树内，它们就是一个调度周期内要兼顾的作业们

- 查找时间复杂度O(log n)

### 总结：

本章从另一个出发点，讨论了调度算法，从`Lottery`到`Stride`，最终获得完善的`CFS`，其中大多是知识性的内容，用表总结它：

| 维度             | Lottery           | Stride                                   | CFS                                                                 |
| -------------- | ----------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| **决策性质**       | 概率抽签              | 确定性记账                                    | 确定性 + 加权记账                                                          |
| **份额载体**       | `ticket`（无默认值）    | `ticket`（无默认值）                           | `nice` → `weight`（默认 0；表为公比 1.25 的等比数列）                             |
| **记账量**        | **无**             | `pass`（初值 0）                             | `vruntime`                                                          |
| **选择规则**       | 随机数落在谁的票区         | 选 `pass` 最小                              | 选 `vruntime` 最小                                                     |
| **时间片**        | 固定，到点重抽           | 固定 quantum                               | 动态：`weightᵢ/Σweightᵢ × sched_latency`（公式①），不足 `min_granularity` 则兜底 |
| **精确性**        | 长期概率收敛；短任务很不公平    | 调度周期内精确（次数 = `lcm / stride`）             | 周期内精确；被兜底和晚切打断后退化为**长期收敛**（记账还在）                                    |
| **新作业初值**      | 无历史，直接发票即可        | `pass` 没有合法初值（设 0 → 垄断）                  | `vruntime` 取树中最小值                                                   |
| **分配问题**       | 票数完全推给人           | 同左，另多一个 `pass` 初值问题                      | `nice` 有默认 0 兜底、`fork/exec` 继承；**想区分才需人配**                          |
| **数据结构 / 复杂度** | 链表（降序可减少遍历）· O(n) | 最小堆 · O(log n)                           | 红黑树 · O(log n)，**只放 runnable**                                      |
| **记账规则**       | 跑完不更新任何状态         | `pass += stride`，`stride = 大常数 / ticket` | `vruntime += (weight₀/weightᵢ) × runtimeᵢ`（公式②）                     |
| **定位一句话**      | 用随机换简单            | 用记账换精确，代价是全局状态                           | “升级版 Stride”：动态时间片 + 加权 + 红黑树                                       |
