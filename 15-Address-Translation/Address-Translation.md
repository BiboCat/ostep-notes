#### 零、地址转换

此前学习了地址空间的内容，引入了内存虚拟化的概念，它让每个进程以为自己占有整个内存，实现内存的共享。而本章介绍的是，内存虚拟化的解决方案——地址转换。

在进程的地址空间中，进程看到的地址，被称为虚拟地址。数据需要真正的存在内存条中，所存内存条空间的地址，就是物理地址。**如果我们拿到任意一个虚拟地址，就能获得一个唯一对应的物理地址，那地址空间的"从0开始、空间连续、互不干扰"的要求就不难实现了**——这就是地址转换。

本书关于内存虚拟化的所有后续章节，都在讨论如何实现这种一一对应的地址转换。本章的主角是`base-and-bounds`，它是最理想情况下最简单的，同时也是很高效的一种方案。

地址转换的根本需求正如方才所说，拿到一个虚拟地址，就应该能得出一个唯一的物理地址；但实际情况下，要考虑设计一个地址转换机制，还有更多其他的需求，比如高效性——这些特质我们会在每一个转换设计的讨论中展开！

#### 一、三个假设

在15.1小节，作者提出了三个简化假设。**它们被用于引出本章主角`base-and-bounds`，这个设计在这些假设中做得很好；同时对这些假设的依赖正是`base-and-bounds`的短板。**

三个假设：

- 地址空间必须**连续**存放在物理内存中；

- 地址空间**小于**物理内存；

- 每个地址空间**大小相同**；

*至于15.2小节，讲为什么需要地址转换，咱们就不展开了。*

#### 二、Dynamic Relocation ：base & bounds

15.3小节，讲的是`base-and-bound`的逻辑！

**转换机制如下：**

- **CPU有两个特殊寄存器：`base`和`bounds`**

- **`base`是基址**，参与地址映射计算
  
  - 映射计算公式：**`physical address = virtual address + base`**

- **`bounds`是界限**，管的是"允许访问到哪"
  
  - **`va >= bounds` 或 `va < 0`时，越界**→ CPU 抛异常 → 通常杀掉进程
  
  - `bounds`有两种定义，逻辑上等价：①存地址空间大小（先比较`bounds`再算`base`）；②存地址空间末尾物理地址（先算`base`再比`bounds`）；书中默认①。

机制非常简单，举个例子一目了然（地址空间 4KB，装在 16KB 处）：

| 虚拟地址 | 物理地址          |
| ---- | ------------- |
| 0    | 16 KB         |
| 1 KB | 17 KB         |
| 3000 | 19384         |
| 4400 | **Fault（越界）** |

回想一下进程切换的场景，CPU只需要切换`base`和`bounds`两个寄存器即可（切换方法可以参考一下CPU虚拟化中关于进程切换的讨论）。

这一节中，作者在ASIDE中讲了一种更古老的机制做对比。
`Software-based relocation`（静态重定位），在加载程序的时候改写指令中的地址，等于是在加载时，一次性转换所有虚拟地址为物理地址，并写回到指令中（修改了指令）。
它的缺点是：①没有保护，程序可以写一个坏地址访问别人的内存（对应`bounds`的功能）；②物理地址搬不动（已写死）——`base-and-bounds`是可以"搬家"的！

#### 三、创建进程时的分配

咱就好奇了，这个机制下，进程创建的时候，怎么分配物理内存空间？

在三条约定的假设下（地址空间**连续**、**小于**物理内存、**大小相同**），OS可以粗暴地把物理内存看成一个**固定大小槽位的数组**。

因此，**`bounds`是一个常量，空闲空间可以由一个记录空闲物理地址区间的数组`free list`管理**。简单展开一下工作流：

1. 从 free list 取一项 → 得到起始物理地址；
2. `base ← 该项起始地址`；
3. `bounds ← 地址空间大小`（**不需要分配，它是常量**，因为假设所有地址空间同大小）；
4. 从 free list 删掉该项，标记已用；
5. 把 `(base, bounds)` 记进该进程的 **PCB / process structure**。

进程结束后的操作，原理也不复杂，不继续展开了。

#### 四、补充

`base-and-bounds`的机制建立在硬件上。地址转换的计算、边界检查、越界拦截抛出异常、异常后的处理程序，都是靠硬件的。15.4小节，作者简单讲解了`base-and-bounds`的硬件实现需求。

这部分内容可以通过上面讲解的机制逻辑推断出，所以作者也称这是一个小结。我们简单过一下：

- **两种 CPU 模式**：kernel（特权）/ user，用一个状态位表示，系统调用/异常/中断时切换；

- **base / bounds 寄存器**（每 CPU 一对，属 MMU）

- **地址转换 + 越界检查电路**（此阶段很简单：一次加法 + 一次比较）；

- **地址转换 + 越界检查电路**（此阶段很简单：一次加法 + 一次比较）；

- **注册异常处理程序的特权指令**（告诉硬件处理程序在哪）；

- 
**能抛异常**：越界访问、用户态执行特权指令。

*不需要全部记忆下来，大多可以通过逻辑推断，现在也没必要去学习具体怎么用硬件实现。*

继续通过内容，15.5小节，作者讲解了OS的4个介入点（同样可以通过推断，仅作补充）：

- **进程创建**：在 free list 里找槽位分配地址空间，标记已用；

- **进程终止**（正常退出或被杀）：回收内存回 free list，清理数据结构；

- **上下文切换**：只有一个 base/bounds 对 → 必须**保存/恢复**到 **PCB / process structure**；顺带结论：进程挂起时 OS 可以**搬移**它的地址空间（deschedule → 拷贝 → 改 PCB 里保存的 base），进程恢复后毫无察觉；

- **异常处理**：boot 时安装 handler（系统调用 / 时钟 / 非法访存 / 非法指令），越界时通常**直接杀掉**进程。

#### 五、分析和总结

这一章读完了，`base-and-bounds`就这么简单，最后让我们看看，它除了地址转换的根本要求达成了之外，还做到了什么？又没做到什么？我们简单举例。

做到的（优点）：

- **效率：几乎是最高效的一档。**每个进程映射所需数据大小=`O(1)`，且与地址空间大小无关。

- **进程切换开销：很低。**只需要额外保存两个寄存器，并且切换很干净。

- **实现复杂度：很低，零软件配合。**核心地址转换，只需要一个硬件加法器。

这些优点产生的原因，几乎都是它太简单了！

没做到的（缺点）：

- **不能共享**：假如100个进程同时跑一个程序，物理内存中就有100份相同的代码！

- **空间不灵活**：地址空间大小相同，假如进程所需内存特别小，也照样占用固定一块连续空间，浪费内存。

- **不能超过物理内存**

- **不能给地址空间设权限**：它根本没做这一块的逻辑，整块区域权限一样，没有"这段只读/这段不可执行"

这些缺点的来源也恰好是它过于简单，依赖三条假设存在。而现代系统的需求是复杂的，所以后续还会迭代性质地学习其他机制！让我们期待其他的机制又实现了什么新功能！

*至于其他知识性的内容，我就不再总结了！因为它只需要记住两个词就行了：`base`、`bounds`！*
