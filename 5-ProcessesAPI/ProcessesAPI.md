#### 一、进程API

在第四章中我们学到，进程可以陷入内核态，其中有一个方式是"**系统调用**"。它是进程请求内核帮忙做事情（一般是涉及高权限的事情），主动陷入内核态。而这其中，进程请求内核的"契约"（或者说能请求的事情），就是**进程API**。

一个进程的完整生命周期（从创建到结束），由内核中的自动流程（如中断、挂起等）+进程API调用。

在本章中，作者介绍的是一些经典的进程API设计。

#### 二、fork() 系统调用

5.1小节中，作者介绍了`fork()`系统调用。

从**功能**上看，`fork`的作用是复制一个自己，本体叫"父进程"，复制体叫"子进程"。让我们接下来看看具体过程。

`Figure 5.1`中作者用C语言举例。暂时<u>忽略`rc`存储的返回值</u>，可以看到`fork()`函数是C语言系统调用的函数。执行该函数，进程从用户态陷入到内核态，并且进程转向执行内核相关的代码。

**内核**中的相关代码，主要逻辑是："创建一个新的PCB并赋值+把子进程塞入进程列表中"。注意此时子进程已经是处于`Ready`的状态了。

执行完内核的代码，就该返回用户态了，也就是回到C语言`fork()`函数，并输出返回值。

上述流程中，最值得注意的是有关**子进程PCB的赋值**，也就是"**复制什么，不复制什么？**"：

| 逻辑上**独立**（各有一份）      | **共享**（同一份实体）                                                                   |
| -------------------- | ------------------------------------------------------------------------------- |
| 地址空间内容（代码、全局变量、堆、栈）  | **打开的文件**：fd 表被复制了，但每个 fd 仍指向**同一个 open file description**，因此**读写位置 offset 共享** |
| 寄存器、PC、栈指针           | 工作目录（cwd）、`umask`                                                               |
| `pid`、`ppid`（父子正好对调） | 终端、进程组、会话                                                                       |

**在这些值中，又有一个最值得关注的点：`PC`**。它<u>是指向父进程此时的位置的</u>，这意味着子进程的PC初始指向的是本次系统调用中内核代码的最后部分（准备返回用户态）。因此子进程继续运行时，第一件事情就是返回`fork()`用户态。——这就是作者说的"**一次调用两次返回**"；至于父子进程谁先返回，则完全看内核对进程的调度策略。

最后让我们回到**用户态返回值**`rc`，它有三种值，**用于区分父子进程返回，以及是否fork成功**！

| 返回值         | 含义                                      |
| ----------- | --------------------------------------- |
| `> 0`       | **我是父进程**，这个数字是**子进程的 PID**             |
| `== 0`      | **我是子进程**，父进程的PID在PCB的PPID字段            |
| `< 0`（`-1`） | 失败，`errno` 为 `EAGAIN`（进程数到上限）或 `ENOMEM` |

展示一下整体流程：

```
用户态：父进程执行到 fork() 的 syscall 指令
    ↓ 陷入内核（特权级切换，但内核栈仍是"这一个进程"的）
内核：kernel_clone() → copy_process()
    · 造一个新的 task_struct（PCB）
    · 复制页表、复制 fd 表、复制信号处理表…
    · 把孩子塞进就绪队列
    ↓ 返回用户态
用户态：① 内核返回到「父进程」的上下文 → 父进程的 fork() 返回 rc = 孩子PID
        ② 内核返回到「子进程」的上下文 → 子进程的 fork() 返回 rc = 0
```

#### 三、exec() 替换

5.3小节作者介绍了`exec()`系统调用。

它和`fork`一样，都是与进程和PCB有关的。从功能上看，它的作用是"替换"，它只在原PCB上做替换。

直接说**PCB的改动**（我只说我现阶段能理解的部分），我们拿`fork`对PCB的操作对比。

| 环节                 | **fork**             | **exec**                  |
| ------------------ | -------------------- | ------------------------- |
| `task_struct`（PCB） | **新建一个**             | **原封不动，一个都不建**            |
| PID                | 新分配                  | **不变**                    |
| 父子关系               | 建立新的                 | **不变**                    |
| 地址空间 `mm`          | 复制 + 页表 COW          | **销毁旧的，新建并装载 ELF**        |
| 代码 / 数据            | 原样保留                 | **全部替换**                  |
| 用户态寄存器现场           | 复制，**只改 `rax`**      | **整体重写**（`ip`=入口，`sp`=新栈） |
| fd 表               | 复制一份（指向同一 open file） | **保留**（只关 `CLOEXEC`）      |
| 进程数量               | **+1**               | **不变**                    |
| 进程状态               | 新增一个 **READY** 节点    | **状态不变**（进程仍在 RUNNING）    |
| 结束后                | 两条延后返回路径             | **不返回**（见下）               |
| 失败时                | 简单：什么都没建成就退出         | **必须回滚**：旧程序要继续跑          |

简单来说，就是PID、PPID、进程列表中状态不变；而用户态寄存器现场、内存、代码等重新加载；关于`fd`，因为真正操作文件的是内核，用户态进程只能拿到`fd`所以一般不会变。

另外是**返回操作**，`exec`会重置原来的进程为新进程，那么原来的调用就完全找不到返回点了，自然就不会返回。而关于失败的处理，`exec`的内核执行逻辑是，必须先做完所有可能失败的操作后，再重置PCB，因此它被设计为可以回滚。

最后我提供一个内核执行路径作为参考（因为我现在也不能完全看懂）：

```
sys_execve()
 └─ do_execveat_common()
     ├─ 打开目标文件、读 ELF 头、检查权限 → 装进一个"待定包" bprm
     ├─ search_binary_handler() → load_elf_binary()
     │   ├─ 【关键】到这里为止，所有可能失败的事都做完了
     │   ├─ begin_new_exec() / exec_mmap()
     │   │    ├─ 丢掉旧的 mm（旧地址空间整体销毁）
     │   │    └─ 新建 mm：映射新代码段、数据段、新栈、vDSO
     │   ├─ 把 argv/envp 复制到新栈上
     │   ├─ do_close_on_exec()   → 只关标了 CLOEXEC 的 fd
     │   ├─ flush_signal_handlers() → handler 重置默认（SIG_IGN 的不动）
     │   └─ start_thread(regs, elf_entry, new_sp)
     │        → regs->ip = 新程序入口，regs->sp = 新栈顶   ← 现场被"重写"
     └─ 返回用户态，但**返回到新入口**
```

#### 四、wait() 等待

5.2小节作者介绍了`wait`。

它的功能承接自`fork`。`fork`能创建一个子进程，而`wait`则让父进程阻塞`Blocked`（停止执行），直到（指定的）子进程完成。

`wait`和`waitpid`功能大致相同，区别在于后者可以通过pid指定子进程。而他们的返回值，有两种情况：

| 返回值   | 含义                                     |
| ----- | -------------------------------------- |
| `> 0` | **被回收的那个子进程的 PID**                     |
| `-1`  | 失败，通常是 `errno == ECHILD`（**我根本没有子进程**） |

#### 五、关于以上三个系统调用API的杂谈

5.4小节中，作者以**`fork`和`exec`为什么分开**为讨论点展开。

它们都是为了进程创造而生，先`fork`，再`exec`，即可创造一个新的进程——为什么创造进程一件事要分两个API呢？

作者给的观点是："**这样存在一段`fork`之后，`exec`之前的空隙，空隙中可以修改运行<u>环境</u>等，于是能有更多创造空间**"。——这个观点的核心在于环境一词。

**在举例子之前**，必须要知道的是：shell只是一个进程，它不是内核，也是用户态的，但它可以帮你执行命令（创建对应进程执行）。下面展示shell创建进程提供服务的一般流程：

```
| shell打输入提示符，等待输入
| 用户输入命令
| shell在文件系统中找到对应可执行文件
| shell系统调用fork创建子进程
| shell系统调用exec替换子进程为命令进程
| shell系统调用wait等待命令结束
| 命令结束，shell回到提示符
↓
```

然后，作者举了**重定向的例子**。命令`wc p3.c > newfile.txt`是典型的输入重定向到文件中。单独执行`wc`命令，输出是标准输出；若加上重定向，则会在`exec`之前，把子进程`fd`表中标准输出的项（`fd 1`）关闭，再打开目标文件，`fd 1`换成目标文件，这就是环境的改变。
(补充：进程`fd`表分配从0开始找最小空闲号)

还记得上面系统调用的知识么——`fork`和`exec`都保留了原进程的`fd`表内容（无论是复制还是不修改）。

#### 六、信号

一个进程的生命周期，除了系统调用外，还和**信号**关联密切。

**信号可以理解为内核对进程的命令**。一个信号的生命周期分为三个阶段："产生"、"投递"、"处理"。

- "产生"：某些系统调用，让内核执行代码时，可能会产生信号；内核自己在管理和调度进程时，也可能会产生信号；还有一种特殊的方式，终端驱动。

- "投递"：信号由内核投递给目标进程，这件事全权由内核负责，无法参与。

- "处理"：信号被进程接收，最终由进程自己实施，此时是用户态。

仔细来说，**信号的产生有4种来源**：

| 来源                         | 例子                                                               | 经过 API 吗     |
| -------------------------- | ---------------------------------------------------------------- | ------------ |
| ① 进程调 `kill()` / `raise()` | `kill(pid, SIGTERM)`                                             | **是**        |
| ② 内核因故障产生                  | 除零 → `SIGFPE`;野指针 → `SIGSEGV`                                    | **否**,你什么都没调 |
| ③ 内核因资源/策略产生               | OOM killer → `SIGKILL`;子进程退出 → 父进程收 `SIGCHLD`;写断掉的管道 → `SIGPIPE` | **否**        |
| ④ 终端驱动(行规程)产生              | 你按 `ctrl-c` → 驱动把**字符**翻译成 `SIGINT`,发给**前台进程组**                  | **否**        |

最后说一点：**信号被记录在PCB中，作为"待办"存在，但不属于机器状态**。
相关字段有：handler表、屏蔽字mask、pending集合。

涉及PCB，那么联想到`fork`和`exec`对此的操作。

| 信号相关状态                    | fork 之后          | exec 之后                                             |
| ------------------------- | ---------------- | --------------------------------------------------- |
| **handler 表**（每个信号的处理函数）  | **完整继承**（逐项复制）   | **重置为默认 `SIG_DFL`**<br>（**例外**：已设为 `SIG_IGN` 的保持忽略） |
| **屏蔽字 mask**（哪些信号暂时不处理）   | **继承**（复制一份）     | **保留不变**                                            |
| **pending 集合**（已到但未执行的信号） | **清空**（子进程从空集开始） | **保留**（同一个进程，信不丢）                                   |

简单分析一下。`handle表`的处理方式不同，是因为它指向的处理方式在进程的地址空间内——`fork`继承，因为同一个表还能用；`exec`重置为默认，因为表指向的地址空间位置已经失去原本意义。
