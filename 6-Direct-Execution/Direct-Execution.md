#### CPU虚拟化

承接第四章的内容，第四章主要讲了关于CPU执行机制的抽象概念：机器状态、进程状态机、进程API。在第四章中，对机器状态和进程状态机做了必要的描述。在第五章中，作者展开讲解进程API。**进程API发生在内核与单一进程之间**。

本章，讲解内核是如何让多个进程共享同一个CPU的，也就是真正的虚拟化的部分——前面两章如果带着"所有进程同时在跑"的视角，也是能够说得通的。本章第一次完整地讲解了CPU虚拟化这个事实。

简单地说，就是在讲："**内核如何把进程放到CPU上跑，并进行进程的切换**？"。这个问题发生在**内核与多个进程，以及单一的CPU之间**。

#### 受限直接执行（Limited Direct Execution）

作者在6.1小节，给出了这个问题的基本技术本体——受限直接执行。

这个基本技术的想法分为两个部分：直接、受限。

- 直接 指的是"让进程直接放到CPU上跑"，CPU一条条取指直接执行。这样的好处是极快，它考虑的是效率。

- 受限 指的是不能完全地让进程拥有CPU的所有权限。如果是单纯的直接执行，内核的权限检查、策略调度的功能将不会生效，它考虑的是功能。

作者对此的原话是：

> without limits on running programs, the OS wouldn’t be in control of anything and thus would be “just a library” — a very sad state of affairs for an aspiring operating system!

当然不能让内核只在旁边看着！接下来第一个关键问题是：如何保证执行速度的同时，让进程拥有一定限制以让内核介入？

#### 受限操作

作者在6.2节讨论了这个问题。——其实在第四章的笔记中，我也简单了解了一下。

**第一个设计**是"**CPU的模式位（权限态）**"，也就是**用户态和内核态**。进程直接跑在CPU上，但是此时CPU处于低权限的用户态。这样进程就不能直接在CPU上执行高权限的操作，比如内核想要掌管的I/O操作，用户态CPU是不能访问文件的。

**第二个设计**是**`trap`**，用户态可以**陷入**内核态。进程/CPU陷入内核态后，转而执行内核的代码。这样执行高权限操作的就不是进程，而是内核。

关于`trap`，第四章学习知识框架的时候，我作了扩展学习。进程的权限态是CPU权限态的逻辑转喻。第四章相关内容还补充了用户态陷入权限态的方式，包括系统调用、中断等。

**第三个设计**是**陷阱表`trap table`**，它是所有`trap`方式的索引。当`trap`发生时，有很多种情况，内核需要根据不同情况跳转到不同位置的内核代码，而`trap table`就是做这个的。

`trap table`在逻辑上，只能允许内核接触，属于高权限（内核态），因此它不能由任何进程创建。所以**`trap table`事实上是在开机时，没有任何进程创建时（此时CPU天然处于内核态）初始化并装载（存在内核的内存中，指针存在特定硬件位置）。而后一直不能被修改直到下一次开机**。

来看一个反例。"不能由任何进程创建"的要求，实际上是严格划分权限的要求——如果一个进程能自己指定陷入内核态后去执行哪里的内核代码，那么权限态划分将毫无意义。

**第四个设计**是**系统调用号**，**注意所有系统调用的`trap`，都共享一个`trap table`表项**。而内核帮忙做什么事，由参数系统调用号决定。

此外，内核执行代码前，还会对接受的用户态传递的参数进行**参数检验**，防止出错。

总的来说，这四个（五个）设计，是为了保证进程直接上CPU快速执行的同时，让内核有参与和控制空间。这其中的关键词是"权限"——保证权限严格分离。

#### 陷入至内核态

6.3小节，在建立了受限直接执行的机制模型上，作者讲述了内核切换进程的过程。

在第四章的学习中，我们简单了解过，进程切换需要保留机器状态，它们是必要的上下文。每次切换，保存现在的，加载新来的，似乎就可以了——但问题是，进程在CPU上跑的时候，意味着内核没在CPU上跑，内核不在场谁来做调度和切换呢？

哦！很显然，这是"直接执行"导致的另一个大问题，它不是权限问题。

**第一种方案**是**协作式**，它主要靠的是进程主动触发。内核无法无理由地接管CPU，一般靠以下方式：进程系统调用、进程结束唤回内核`yield()`、进程触碰非法操作。

注意到**这些方式的主语都是进程**，也就是说只要一个进程一直不触发这些规则，它就能一直享用CPU（直到关机）。——比如进程写了一个死循环`while(1)`！

**第二种方式**是**定时器中断（非协作式）**，直接让硬件每隔一段时间，强制打断进程让内核接管。我们知道，中断是一种陷入内核态的方式；中断发生后，由`trap table`指导下一步干啥。

值得说的是，定时器中断是可设置的。它可以设定定时器的时间、开关等，不过这些都是特权操作，用户态不能修改。

在现代系统中，往往是两种方式结合在一起，和我们之前学到的陷入内核的方式有关。

##### 内核栈和上下文

在第四章中我们了解过，进程的寄存器上下文有两类，一类是执行用户态代码的寄存器上下文，另一种是执行内核态代码的寄存器上下文。当时提到的数据结构是`tf`和`context`。

`tf` 的全称是`trapframe`，可以译为**内核栈**，它的值是内核栈的指针。内核栈在每个进程的内存空间中都存在，**每个进程都有一个自己的内核栈**，用于陷入内核态后跑内核代码。

所以首先需要指正的是：**内核只是一段代码，从来就不是一个进程，之前关于它的主语性描述都只是为了方便。在这个真实的视角下，内核更像是一套规则，执行者不是自身，而是进程们。**

`tf`与用户态寄存器上下文有关，是因为用户态的寄存器就是保护在内核栈中的。它首先是内核栈的指针，然后才发挥保护用户态上下文的功能。

`context`是专门存内核态寄存器上下文的结构。扩展说明一下，在书上的老版本`xv6`中，它是PCB的一个成员，是直接记录在PCB结构体上的；而在一些新版中，它被保存在内核栈上，`context`是内核栈上某地址的指针。 

##### 我关于内核的认识V2

那好奇了，**既然内核不是进程，是代码，那么以前学过的"进程列表"这个全局数据，放在哪呢？**——这涉及到了内存虚拟化的内容！

先下一个定义：**内核=内核代码+全局数据**；**内核空间=内核+各进程的内核栈**。我们把内核的存在形式讲清楚。

再简单解释一下**内存虚拟化**：进程获得的内存空间，地址从0开始且连续，但这只是逻辑上的——内存空间的物理实体可能是零散的（以页为单位），虚拟地址则是一种映射。（非正式解释，仅作辅助理解）

内核代码和全局数据，在开机时就占用好了物理内存的一部分。创建进程时，对应内核栈被分配物理内存。每个进程的虚拟内存空间中，都映射有上述三个物理内存（即进程可以在自己的内存空间中找到内核代码、全局数据、自己的内核栈）；且关于内核的部分，从虚拟内存的高地址开始写，占用虚拟地址的最高部分。

最后补充一点：虚拟内存映射内核栈，不止映射该进程自己的内核栈，实际上映射了所有进程的内核栈。但是进程处于内核态时，不会乱用别人的内核栈。

有点跑题了，现在回到进程切换上。

进程在切换(`swtch`)时，都是处于内核态的。此时原进程的用户态上下文早已保护在内核栈中。现在还需要保护的上下文是内核寄存器。让我们跟随作者的例子分析：`Figure 6.4`。

```c
struct context {        // 偏移
  int eip;              //  0     返回地址（断点）
  int esp;              //  4     栈指针
  int ebx;              //  8
  int ecx;              // 12
  int edx;              // 16
  int esi;              // 20
  int edi;              // 24
  int ebp;              // 28
};//这个不能少，否则下面的偏移将无意义
```

```
# void swtch(struct context *old, struct context *new);
# 传递进来的，是两个context结构指针，不管它们存在于PCB还是内核栈中
.globl swtch
swtch:
    # 存old的8个寄存器
    movl 4(%esp), %eax #这句把old指针放在了eax中
    popl 0(%eax) 
    # save the old IP
    movl %esp, 4(%eax) # and stack
    movl %ebx, 8(%eax) # and other registers
    movl %ecx, 12(%eax)
    movl %edx, 16(%eax)
    movl %esi, 20(%eax)
    movl %edi, 24(%eax)
    movl %ebp, 28(%eax)
    # 加载new的8个寄存器
    movl 4(%esp), %eax # 这句把new指针放在了eax中
    movl 28(%eax), %ebp # restore other registers
    movl 24(%eax), %edi
    movl 20(%eax), %esi
    movl 16(%eax), %edx
    movl 12(%eax), %ecx
    movl 8(%eax), %ebx
    movl 4(%eax), %esp # stack is switched here——换esp相当于换栈
    pushl 0(%eax)
    # return addr put in place
    ret
    # finally return into new ctx
```

要点提示：

- **换进程的本质是：换内核栈、换`eip`、还原现场——这是8个寄存器在做的；**

- 换`esp`就是换内核栈；

- `popl 0(%eax)`保护`eip`，取的是当前内核栈栈顶的值，这是因为调用`swtch`时，即`call swtch`会在跳转前，把返回地址压进栈（一个很符合直觉的汇编知识）。

- `pushl 0(%eax)`和`ret`是在取`eip`，因为`ret`的功能就是取栈顶值到`eip`上。这么写是因为`eip`本身不可以直接编辑赋值。

总结：本质换8个内核栈寄存器上下文，只不过涉及到一些汇编设计。
