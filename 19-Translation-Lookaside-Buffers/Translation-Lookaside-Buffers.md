#### 零、快速地址转换——TLB

上一章引入分页时，涉及到时间和空间开销问题；其中时间开销是指，由于页表存在于内存中，因此每次访存都必须访问额外访问一次页表，时间翻倍。

而本章就是解决时间开销的问题，方法是TLB（Translation Lookaside Buffers）。

#### 一、TLB基本机制

TLB是硬件内部的一块缓存，用于存储一些`VPN -> PFN`的映射，以完成硬件级别的快速映射；它的作用类似CPU与主存之间的cache，因此作者说TLB更贴切的名字应该是：`address translation cache`。

TLB存在硬件中，其中的映射不可能是完整的页表（TLB只有部分映射）；因此同cache一样，使用TLB时会出现**命中和未命中两种情况**。原文`Figure 19.1`是两种情况下的机制：

- **TLB命中**：检查权限位 -> `VPN -> PFN`转换，拼出物理地址 ->访存

- **TLB未命中**：查页表 -> 检查权限位 -> `TLB_Insert`**插入这条映射至TLB** -> 再次TLB映射

可见，命中时是硬件级别的开销（与访存相比几乎为0）；未命中时就是正常访问页表的开销，回到分页的时间开销上。——**命中次数越多，节省的时间开销就越多！如果频繁使用某些页，命中次数就会很多！**

**TLB的优势区间在于空间局部性和时间局部性**：

- **空间局部性**：比如连续访问一个数组，该数组元素挤在同一页，那一页被加载到TLB中，那么TLB命中率就会很高，最坏只有第一次访问数组时没有命中。

- **时间局部性**：比如一个简短的循环，在一定时间内来来回回访问某几页，只要这些页数量不超过TLB的缓存数量上限，那么最坏只有第一次循环时未命中，命中率很高。

- 此外，可以预见的是：**页越大，命中率越高**。页越大，空间局部性越强；页越大，页就越少，时间局部性也会增强。

#### 二、谁处理TLB未命中

**TLB的机制就是这么多**，并不复杂，后续进行几个问题的扩展讨论。
19.3小节，作者讨论的是一些实现问题：谁处理TLB未命中？

有两种实现方式，硬件管理和软件管理：

- **硬件管理**：硬件使用`PTBR`查页表（就和上一章说的那样） -> 硬件查到后写回TLB -> 最后重试

- **软件管理**：硬件TLB未命中只抛出异常 -> 陷入内核 -> OS查页表 -> OS用特权指令写TLB -> 返回用户态并重试

注意一下两个细节：

①**避免无限`TLB miss`**：陷入内核态，OS接管CPU是需要执行内存中的内核代码的，这部分内核代码不应该通过地址转换找到，否则可能在寻找这部分代码时再次触发`TLB miss`。因此，这部分内核代码的位置一般以物理地址记录（记录在哪则是内核代码负责的问题，这里不回答）。

②**注意返回地址**：回忆系统调用的知识，进程从内核态返回用户态时，返回地址一般是用户态系统调用指令的下一条指令；而此处由于需要<u>重试</u>，因此返回地址是原来引发`trap`的指令，即原先访存但`TLB miss`的指令。

软件管理优势很明显：**灵活**（页表可以是任何数据结构）；而且逻辑推给软件，使得硬件设计变简单。

#### 三、TLB里有什么？

19.4小节，作者讨论了"从逻辑上，TLB项需要哪些字段？"

首先是`PFN`和`VPN`，这个是根本功能，必须存在；
其次是有效位`valid`，否则无法区分哪些条目是确实记录确实有效的；
还有保护位，记录这一页的操作权限（可读/可写/可执行）；

除了`valid`（它通常用于TLB自身管理），这些都是我们在`PTE`中了解过的字段，它们在逻辑上必须保存在TLB项中，是因为："**TLB是用于替代访存的，需要记录访存查页表时可能用到的所有信息**"——这就是TLB字段设计的逻辑原则。

此外作者还在本小节中提到了`D`（脏位），这个在后续章节才展开；作者还提到了`ASID`，这属于本章中关于TLB替换、刷新的策略内容（稍后讨论）。

#### 四、机制补充：上下文切换

站在页表的角度，进程切换时，使用的页表要被切换（切换`PTBR`）；因此在TLB的角度，进程切换时，也意味着旧的TLB项不能再使用了。这时候TLB会怎么做呢？

这里有两种机制：

- `flush`整体刷新：把TLB清空（本质上是把`valid`全置零）；`flush`是一条特权指令。

- `ASID`：给TLB项增加一个`ASID`字段，用于标识表项所属进程；同时额外维护切换一个寄存器，只有`ASID`的值与该寄存器的值相同时（表示该表项属于当前进程），才能使用该表项。

`flush`的方案简单，但是每次切换进程后，TLB从头开始维护，命中率会暂时降低；`ASID`的方案下，TLB中会出现不同进程的映射缓存。

它们不是非此即彼的，它们只是机制，而非二选一的策略。

#### 五、策略补充：TLB替换

TLB总有满的时候，当一个表项需要在此时写入TLB，就必须覆盖一项写入——选谁？

**这个策略问题，并不是TLB的问题，是属于所有缓存的问题**（比如它在cache中也存在）。一般来说，有几种方案：`FIFO`（先进先出）、`RAND`（随机）、`LRU`（最近最少用）、`LFU`（最不常用）......

*这些策略，都不在本章展开。*

值得注意的是，刚刚讨论的`ASID`，位数是固定的，即编号数量有限；一旦进程多了，`ASID`必然不能给所有进程编号，这时候就又得考虑，哪些进程的`ASID`被取消？
——所以说，替换是所有缓存的共同问题。

#### 六、总结

本章主要内容为介绍TLB的基本机制——它是页表的缓存。

- **TLB命中**：检查权限位 -> `VPN -> PFN`转换，拼出物理地址 ->访存
  
  - TLB命中靠的是**空间局部性**和**时间局部性**，并且页越大，命中率越高
  
  - TLB作为页表的缓存，命中后就不需要查页表，因此**TLB需要记录访存查页表时可能用到的所有信息**（比如权限位）

- **TLB未命中**：查页表 -> 检查权限位 -> `TLB_Insert`**插入这条映射至TLB** -> 再次TLB映射
  
  - TLB未命中的行为有两种实现方式：硬件和软件；软件交给OS且更灵活
  
  - `TLB_Insert`插入时，涉及到缓存通用的管理策略问题【本章未展开】
- **进程上下文切换**时，涉及TLB的两个机制
  - `flush`特权指令清理缓存——会导致命中率暂时下降
  - `ASID`标识进程，让多个进程的`PTE`缓存同时存在与TLB中

回到最初的问题，TLB确实减少了分页的时间开销；
本章提出的问题（是其他章节的引子），有：TLB中具体的字段（本身页表的字段就没有完全摊开）、缓存管理策略；
进程上下文切换的两个机制，虽然篇幅不长，但是已能建立大致模型。
