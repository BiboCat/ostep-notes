#### 一、开篇的核心问题

文章提出了第一个问题，同时运行多个计算机进程时，仅有一个CPU如何正常运行——虚拟化CPU（时间共享）。有点像信道划分的时序逻辑吧。

- 除了时间共享，TIP方框介绍了另一种叫"**空间共享**"，它对应的例子是磁盘。

这个虚拟化的代价是性能，一个物理CPU算力总量是一定的。

文章接着说，时间共享不是简单的均分，其中还可能存在一些做决策的算法。比如多个进程运行时，优先运行哪一个程序。——这玩意称作为"**策略(policy)**"

文章有一句话，出现在TIP中，叫**机制与策略分离(separate policy and mechanism)**。我们已经知道了策略，而机制指的是底层的方法/协议，机械地实现某个功能。
形象的说，机制回答"how"，而策略回答"which"。

#### 二、机器状态 machine state

为了使CPU能够实现时间共享——本质上是停下一个进程，再运行另一个进程，需要解决一个问题："停止一个进程的时候要保存什么，才能使得下一次能够完美衔接这个进程的运行状态？"

机器状态(machine state)被定义解决这个问题。它就是停止一个进程时，必须保存的进程运行状态——相当于游戏存档。

内容主要有：

- PC ：程序被执行靠CPU读取指令内存中的机器码，PC是指向当前指令地址的寄存器

- 其他寄存器：执行进程时所用到的数据，暂存在通用寄存器中

- 内存：程序被拉到内存中跑起来才成为进程，程序代码、数据、全局变量、堆栈等都在内存中

- I/O信息：书上举的例子是"这个进程打开了哪些文件"，形象的说是，这个进程有哪些跟外界打交道的通道+每条通道走到哪一步了？通道不止文件，终端、管道、网络连接、设备，全都算——在Linux中，一切都是文件（下面说）。

##### 文件

**文件**是硬盘上的一大串字节，本身没有任何标识。一个文件唯一对应一个`inode`；而文件名仅仅是一个字符串，用于标识文件。

我们见到的目录，肩负着文件名映射`inode`的功能，帮助使用文件名查找到文件。因此文件名不直接指向文件，而靠目录映射为`inode`后指向文件。

回到`inode`，它不仅仅是一个编号，编号中存在信息 ：大小、权限、属主、三个时间戳、数据块指针（定位文件位置），以及自己的编号。——就类似身份证，再细致的不展开说。

回到进程**<u>打开文件</u>**。进程是用户态，它向内核（内核态）申请打开某个文件时：
1、内核会定位到该文件的`inode`，并检查进程是否有权限打开该文件；
2、内核会打开该文件，在内核内存中建立一个**记录**，维护打开文件的信息（比如读写位置）——可见，访问文件这事，是内核全权负责。
3、内核最后会向用户态进程，交付一个"**文件描述符(`fd`)**"；同时，内核维护每个进程一张的**`fd`-打开文件记录** 的表。——可见，`fd`仅仅是一个凭证。

最后，说说"一切皆文件"的设计，文件的存取，对于进程来说是I/O；而其他方式的输入输出，其实也是通过文件来完成的。Linux统一了接口。

我暂时不展开细说，我列一个表提供大概的概念：

| 你以为是       | 在 Linux 里也是"文件"         |
| ---------- | ----------------------- |
| 键盘/终端      | `/dev/tty`、`/dev/pts/0` |
| 黑洞（写进去就没了） | `/dev/null`             |
| 整块硬盘       | `/dev/sda`              |

小结：

- 进程是用户态，内核是内核态，对文件的直接操作由内核完成，用户态通过`fd`获取服务。

- Linux一切皆文件，统一了关于机器状态I/O信息保存的方法：保存`fd`。因为进程仅仅掌握`fd`，并且进程被切走，不是相关的内核文件服务被切走。

- 文件的组织形式核心是`inode`，目录提供文件名到`inode`的映射。

#### 三、进程API

在4.2小节，作者介绍了进程API的概念。

进程API是内核关于进程的相关接口，是"内核提供给进程操作的接口"。在本章节中，作者仅仅是引入了该概念(具体在后续章节)，并说了接口中必须有的五类：

- `Create` 创建新进程

- `Destroy` 强制杀死进程

- `Wait` 等待进程结束

- `Miscellaneous Control` 其他控制，比如挂起`suspend`

- `Status` 查询状态信息

#### 四、从程序到进程

4.3小节，作者介绍了从程序到进程的六步。

1、把硬盘数据读到内存。这里分早期和现代OS：早期OS一次性全加载完，而现代OS有分页

2、分配并初始化栈(`stack`)。

3、往栈里填`main()`的参数。（`main`是一个概念简化，指程序入口点）

4、分配堆(`heap`) 。

5、I/O初始化。进程默认有三个`fd`，标准输入0、标准输出1、标准错误2。

6、跳到入口点`main()`执行。

这个描述并不复杂，它基本都是C语言学习时能接触到的相关概念。

#### 五、进程状态机

4.4小节，作者介绍了进程的基本状态。

一个进程在任一时刻只能处于三种基本状态之一：

- `Running`（运行）：正在 CPU 上执行指令。
- `Ready`（就绪）：可以跑，但 OS 此刻选择不跑它。
- `Blocked`（阻塞）：它在等某件事（典型是发起 I/O 后等磁盘返回），所以不能跑。

三种状态的转换方式，由原文`Figure 4.2`给出。

其中的术语需要拿准：

- `ready → running` 叫 `scheduled`（**被**OS调度）；
- `running → ready` 叫 `descheduled`（**被**OS取消调度）；
- `running → blocked` 是进程自己发起的（发起 I/O），
- `blocked → ready` 是外部事件把它唤醒（I/O 完成）。

而后作者给了两个表当例子，展现了两个不同的情况：

- `Figure 4.3`：两个纯 CPU 进程。P0 一直`Running`，P1 一直`Ready`，P0结束P1才上。CPU 利用率 100%。
- `Figure 4.4`：P0会做 I/O。P0跑到第4个时间片发起I/O变`Blocked` → OS 让 P1 上（CPU 不空转，**提高资源利用率**）→I/O完成P0回到`Ready`→ **但 OS 没有立刻切回 P0，让P1跑完** → 最后P0跑完。作者在这里问："这个决定好不好？"——这正是**调度策略**要回答的问题。

#### 六、数据结构：OS进程管理

4.5小节，作者介绍了OS是如何管理进程的。

进程是OS在硬件（CPU等）之上定义的抽象，进程是属于OS这个软件的概念。因此OS需要管理这些抽象，实际在代码落成上，就是OS这个程序中的数据结构——这正是该节所介绍的。

- 进程列表`process list`
  
  - 功能是所有进程的登记册，记录有哪些进程，这些进程处于什么状态。
  
  - 实际形态通常是**双向链表**，但所谓进程列表，只是一个统称，实际所用数据结构不止一个链表，而是由不同功能的链表（如`runqueue`表示可以执行的进程）组成的集群。

- 进程控制块`PCB`
  
  - 这是进程最核心的结构，每个进程独一份，里面有：PID、状态、父进程指针、**寄存器上下文**、栈指针、I/O信息等完整的进程信息，包括了**机器状态**`machine state`
  - 其中还含有多个链表节点，供进程列表中的链表链接使用。

- 寄存器上下文`register context`
  
  - 这是一块特定内存，用于存储机器状态中的通用寄存器部分。

接下来看原文中举的具体例子`Figure 4.5`，展示的是`xv6`操作系统的数据结构（一个小号的Unix系统）。这里的重点是展示了`PCB`记录机器状态的功能。此外，还有一个关于寄存器上下文的额外知识：

```c
struct context {
int eip;
int esp;
int ebx;
int ecx;
int edx;
int esi;
int edi;
int ebp;
};
//这是默认寄存器

enum proc_state { UNUSED, EMBRYO, SLEEPING,
RUNNABLE, RUNNING, ZOMBIE };
//六个定义的进程状态（原先介绍的三个是最基本的，不代表所有的都是）

struct proc {

//context和tf都是寄存器上下文，这是一个额外知识。
};
```

##### 用户态和内核态

**用户态和内核态本身的定义是CPU的权限状态！**

- 用户态`ring 3`，CPU权限很低，比如不能读写磁盘和网卡。

- 内核态`ring 0`，CPU全部权限，什么都能干！

但这个说法，能够转喻到进程上。
虽然进程是OS层面的、CPU之上的说法，但是在某一时刻下，CPU是被一个特定进程占用的。**因此CPU的两态，可以说成进程的两态。**

进程的两态，也是针对权限说的。正常运行进程，对应C语言代码层面，是跑在用户态的。跑到某些函数，需要调用内核代码时，进程会转向内核态，CPU也会变成内核态，**并且执行的指令，不再来自进程的内存，而是来自内核**！

那么关键来了，转而执行内核的代码，在实现上也需要保护原来用户态执行进程的寄存器、栈等（不是完整的机器状态）；内核代码执行完，回到原进程用户态（或中断进程），也需要保持执行内核代码的寄存器和栈——从这个角度看，同一个进程拥有两态，需要保护两套代码执行现场。而这在寄存器层面，就是`context`和`tf`的区别！

- `context`内核态执行寄存器。

- `tf`用户态执行寄存器。

这就是一个`PCB`中有两个寄存器上下文结构的原因。

补充一下用户态何时转向内核态：

| 类型       | 例子                | 谁发起   |
| -------- | ----------------- | ----- |
| **系统调用** | `read()`、`fork()` | 程序主动  |
| **中断**   | 时钟、磁盘完成           | 硬件,随时 |
| **异常**   | 除零、缺页             | 硬件,被动 |

**一个进程的完整"机器状态" = `tf`(用户态现场) + `context`(内核态现场) + 地址空间(内存) + PCB 里的其他管理信息**

##### 内核

刚开始接触真的是十万个为什么...

笼统地说，内核就是直接和硬件打交道的，让一堆电路打包成一个个软件可用的接口，打了软件的地基，在此之上，软件得以开发。

但确切地说，内核不仅仅是和硬件打交道，因为它与硬件打交道的代码不是无条件的，它不仅仅是一个被动的地基，它还有主动的选择。内核可以决定哪个进程先上CPU；以及某个进程权限不足请求系统调用时，它可以拒绝。

**内核和操作系统的关系，是一个定义问题**。狭义的操作系统，就是指硬件之上的这层内核，比如"Linux"的说法（Linux本身就是内核）；而广义的操作系统，可以包括内核的`shell`，以及其他集成环境等，典型的区别是`Ubuntu`和`Android`，他们都是Linux内核，但不是一个操作系统。

另外说说发行版，是刚刚所述两层模型之上的第三层。这涉及到各层的术语，该阶段我也不完全清楚，放一个结构图仅供参考（其他后续学习）：

#### 七、总结

我们采取狭义的操作系统定义，OS就是内核。

进程是OS定义的一个概念，用于多个程序同时运行时的CPU调度问题。这个问题，涉及**执行机制**（如何让CPU切换进程）和**调度策略**（谁先上CPU执行）。本章着重讲解的是执行机制方面的概念。

第一个概念是**机器状态**，进程被切换的时候，必须保留当前的状态，以便下次切换回来继续执行。机器状态包括：PC、寄存器、内存、I/O信息。——这是最粗略的一层。

第二个概念是**进程状态机**，CPU来回切换多个进程，进程也有I/O需求，因此进程们各有不同的状态，内核需要一个管理模型去描述进程。最简单的状态机模型是三态的，`Ready`、`running`、`blocked`。状态机是便于描述内核（OS）管理进程的概念模型。

第三个概念是**进程API**，这是内核对进程开放的操作窗口。进程是内核之上的概念，进程天生处于用户态，它需要内核帮忙做一些事情时，会调用这些API陷入内核态，并交由内核代码执行。

机制大概框架就是这样。最后，拿`xv6`讲解了内核管理进程的代码实现（**数据结构实现**）。最核心的数据结构是`PCB`，它保存了**完整的机器状态**，并且存有各种节点，用于组成内核用于管理进程的进程列表。
